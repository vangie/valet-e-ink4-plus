# 自建助理的语音引擎（提问 + 通话）

2026-11-23。适用于「云服务」选「自建」（OpenClaw / Hermes）时的提问和通话；官方云（百问、云信等）仍走原来的 `AudioService`。

## 为什么重做

原来的链路是官方（小智）那一套：麦克风 → Opus 编码队列 → 主循环 → 协议层再解码；网关的声音 → 协议层收到就同步塞进解码队列（满了就等）→ 解码 → 播放队列 → 扬声器。三个问题：

1. **播放一停，整条链路一起堵**：解码队列满了，收消息的线程卡在入队上，而它拿着协议层的锁；麦克风上传要同一把锁，于是麦克风也停了。任何「先停播放、再听一下」的做法在这里都听不到声音，还曾经让通话彻底卡死。
2. **不知道声音什么时候真正放出来**：只能拿「交给 I2S 的时刻」近似，误差几十毫秒，还会随队列长短变化，回声对不齐。
3. **白做一次 Opus 编解码**：自建网关要的是 PCM / IMA，麦克风却先编成 Opus 再在协议层解回来。

## 测量（设备实测，见 `main/valet_dev/audio_probe.cc`）

- 扬声器 → 麦克风的延迟在同一个 I2S 时钟下是**固定**的：1735 样本（108.4 ms）。音频循环故意卡 400 ms 后仍不变。
- 但蓝牙音频芯片偶尔会整块丢 / 补 80 个样本（5 ms），延迟跳到 1656、1495 等。
- 回声**强烈非线性**：1.5～6 kHz 比播出的声音还响 8～11 dB（扬声器失真），用离线最优线性滤波器也只能压 5 dB，常规回声消除（AEC）在这块板上做不好。
- 1 kHz 以下回声很弱（比播出声低 11～16 dB），而人声的主要能量就在这里 → 插话检测只看 150～1000 Hz（`main/audio/talk_over.h`）。离线评估：两段各 30 秒纯回声 0 次误报，插话 0.1～0.25 秒内发现。
- 功放必须在整个会话里一直开着：电源策略默认跟着界面状态开关功放，会吃掉句子开头。
- 板上没有扬声器回采（输入第二声道一直是静音）。

## 结构

```
            ┌────────────── VoiceEngine（main/audio/voice_engine.*）───────────────┐
网关声音 →  │ Play(): 写入播放环（PSRAM，不阻塞）                                  │
            │                                                                      │
            │ I/O 任务（20 ms 一拍，固定顺序）：                                    │
            │   从播放环取 320 点（没有就补零）→ 写 I2S → 读 I2S 320 点麦克风         │
            │   → 记下「这一拍播出去的」和「这一拍录到的」（同一拍号，延迟固定）        │
            │   → 插话检测（只在播放时）→ 麦克风写入上行环                           │
            │                                                                      │
            │ 播放环计数：已写入 / 已播出（样本精确）、最后一次出声的拍号            │
            └──────────────────────────────────────────────────────────────────────┘
                     ↑ Play / Flush / 计数                 ↓ 麦克风帧、插话事件
            ┌──────────────── ValetProtocol ───────────────────────────────────────┐
            │ 收消息线程：解码 IMA → 音量自动控制 → 24k→16k → Play（永不阻塞）       │
            │ 上行任务（新）：取麦克风帧 →（通话）防回声静音 / 人声门 / 补开头        │
            │               → 16k→24k → IMA → appendAudio                         │
            │               （提问）按键期间录下来，松开后整段上传                   │
            │ 确认点：按「已播出样本数」回 acknowledgeMark                          │
            │ 插话：引擎报插话 → Flush 播放环 + cancelOutput + 补上静音期间的开头    │
            └──────────────────────────────────────────────────────────────────────┘
```

要点：

- **只有一个音频任务碰 I2S**，写和读在同一拍里，所以「第 n 拍录到的」和「第 n−5.4 拍播出的」永远对应。
- **网络这边永不阻塞音频，音频也不等网络**：两个方向都是环形缓冲区；播放环 30 秒，满了丢最旧的并记日志。
- **播放计数是样本级的**：确认点、播放进度、「最后一次出声」都按实际写给 I2S 的样本算，不再按包。
- **打断是瞬时的**：Flush 把播放环清空，下一拍就是静音（10 ms 淡出，避免爆音）。
- **防回声**：通话中扬声器在响（以及最后出声后 300 ms，含 108 ms 路径延迟）时上行发静音；一旦判定插话，立刻停播放、放开麦克风，并补上静音期间最后约 0.4 秒（句子开头）。
- **两种模式共用一套**：提问模式只是上行策略不同（按键期间录、松开上传），回答的语音同样进播放环。
- 功放在引擎运行期间一直开着（`PowerNeed::LocalPlayback`）。

## 与原来代码的边界

- `AudioService` 加一个「引擎模式」：自建会话启动音频时由 `Application` 选择；引擎模式下不启动原来的输入 / 输出 / 编解码任务，`ResetDecoder`、`IsPlaybackIdle`、`OutputLevel` 等转给引擎，发送队列始终为空。
- 官方云路径完全不变。
- 墨水屏刷新时音频任务可能抢不到 CPU：这时会短暂断音，但收放计数和延迟对应关系不受影响（实测）。通话中尽量不刷屏（字幕攒着、波形固定）的做法保留。

## 还没解决的

- 回答开头偶尔被音频芯片的自动静音吃掉几十毫秒（扫频测试里看到），需要再测。
- 插话门槛是用 Mac 喇叭扮演用户定的，真人声音要再校一次。
- 插话后补上的开头里混着助理最后半句的回声，网关可能听到一点。
